01 · File Organizer — una carpeta ordenada en un comando

La carpeta de descargas acumula archivos desordenados: PDFs, imágenes, scripts, instaladores y datos mezclados en un solo nivel. Encontrar algo se vuelve lento y ordenar a mano es tedioso. Este proyecto es un CLI de Node/TypeScript que automatiza esa tarea con una regla simple: clasificar cada archivo por su extensión y moverlo a su carpeta de categoría (PDF/, Images/, Videos/, Code/, …). Es seguro por diseño: nunca sobrescribe, nunca borra, es idempotente y admite un modo de ensayo (--dry-run) que no escribe nada. Este dashboard explica cómo funciona y por qué es confiable.

Stack: Node 26 · TypeScript nativo (sin build) Dependencias: 0 en runtime Clasificación: por extensión (función pura) Seguridad: nunca sobrescribe · dry-run sin escrituras Evidencia: 50/50 tests · typecheck limpio

01 El problema: una carpeta que nadie ordenó

Cada descarga, captura y archivo suelto termina en el mismo lugar: la carpeta de descargas. Con el tiempo conviven documentos, imágenes, ejecutables y basura sin ningún orden, y el costo aparece en cada búsqueda.

El costo de no ordenar

  • Reporte.pdf — un documento que necesitas para una reunión, enterrado entre decenas de nombres.
  • foto.png — una captura que querías adjuntar y no recuerdas el nombre exacto.
  • setup.exe — un instalador que ya no usas, ocupando espacio sin que sepas.
  • notas.md — tu propio archivo, confundido con el resto del desorden.

Lo que se quiere

1 · descargas caóticas→ 2 · un comando→ 3 · carpetas por categoría→ 4 · búsqueda inmediata

La idea: una regla simple y determinista — la categoría de un archivo se deriva de su extensión — aplicada por un CLI con modo de ensayo. Nada se pierde, nada se sobrescribe y el resultado se puede revisar antes de escribir.

La pregunta del proyecto: "¿puedo automatizar el orden de una carpeta con una regla simple, sin arriesgar mis archivos?". La respuesta vive en cinco invariantes (los axiomas) que el organizador respeta siempre.

02 Cómo funciona: un flujo de 4 pasos

El organizador separa leer y decidir (plan) de escribir (ejecución). Esa separación es la clave: permite ensayar sin efectos y reportar con determinismo.

1 · scan→ 2 · classify→ 3 · plan→ 4 · move

scan · mover.ts

  • readdir con withFileTypes: distingue archivos, directorios y symlinks sin un stat extra.
  • Solo procesa archivos regulares del nivel superior; filtra directorios, ocultos, symlinks y los archivos de configuración cargados.

classify · classify.ts

  • Función pura por extensión: mismo nombre, mismo resultado. Sin I/O, sin estado global.
  • Extensión desconocida o archivo sin extensión → carpeta miscelánea (Others por defecto) o se omite.

plan · mover.ts

  • Resuelve destinos y colisiones antes de escribir (conjunto de reservas intra-plan).
  • Orden lexicográfico por nombre: reporte estable y determinista.

move · mover.ts + cli.ts

  • mkdir recursivo de la carpeta destino + rename (atómico), con fallback cross-device (EXDEV).
  • En --dry-run esta etapa no ejecuta ninguna escritura (ni siquiera mkdir).
Plan ≠ ejecución. Escanear y clasificar es lectura pura: se puede ejecutar mil veces sin cambiar nada. Solo la última etapa escribe, y solo si no estás en modo de ensayo. Por eso el reporte del dry-run es idéntico al plan real.

La regla: solo se mira la última extensión (archive.tar.gz → gz); un nombre sin punto (LICENSE) o con punto inicial (.env) no tiene extensión → carpeta miscelánea (o se omite si la configuración lo pide). Un archivo que empieza con . además es oculto: por defecto ni siquiera se escanea.

04 Dry-run vs. ejecución real: ensayar sin tocar nada

El modo de ensayo muestra el plan sin escribir una sola letra: ni mueve archivos, ni crea carpetas. Es la salvaguarda para revisar el resultado antes de comprometerte. La única diferencia con la ejecución real es… que no ejecuta.

--dry-run · modo ensayo

  • Imprime el plan con el prefijo [dry-run] en cada línea.
  • Cero escrituras: ni rename, ni mkdir, ni unlink.
  • Perfecto para revisar antes de una corrida real.

Ejecución real · modo normal

  • Crea las carpetas de categoría y mueve cada archivo con rename.
  • Reporta el mismo formato en stdout; los errores van a stderr y el código de salida es 1 si algo falló.
  • Idempotente: una segunda corrida produce 0 movimientos.
En --dry-run el reporte del plan se muestra tal cual se ejecutaría: el mismo orden, los mismos destinos, el mismo conteo Moved: n | Skipped: n | Errors: n. La diferencia es que no pasa nada en disco.

05 Colisiones: por qué nunca se pierde un archivo

¿Qué pasa si la carpeta destino ya tiene un archivo con el mismo nombre? La respuesta: nunca sobrescribir. El organizador añade un sufijo determinista — name (1).ext, name (2).ext, … — comprobando el disco y las reservas del mismo plan.

La regla de oro

  • Si PDF/report.pdf ya existe → el nuevo se llama report (1).pdf.
  • Si report (1).pdf también existe (o fue reservado por otro movimiento del plan) → report (2).pdf.
  • El sufijo es determinista: misma entrada, mismo resultado.
  • Nunca se borra ni se reemplaza un archivo existente (axioma 3).

El caso sutil: reservas intra-plan

Dos archivos de la raíz pueden terminar queriendo el mismo destino dentro del plan. El conjunto de reservas lo impide: el primer movimiento «reserva» su nombre y el segundo elige otro. Probalo abajo.

Escenario — la carpeta PDF/ ya contiene report.pdf de una corrida anterior, y en la raíz hay report.pdf y report (1).pdf.

06 Precedencia de configuración: 5 capas, gana la superior

La configuración activa se resuelve de menor a mayor precedencia. Ante un conflicto, la capa superior gana, y el mapeo se fusiona por extensión (una clave presente sobrescribe o extiende; las demás conservan su valor por defecto — no es un reemplazo total).

07 Los 5 axiomas del organizador

    

      Invariantes que el código respeta siempre. Son el «contrato» de seguridad del proyecto: si un
      cambio futuro los violara, los tests lo detectarían.
    

    

      

        A1
        
La categoría se deriva solo de la extensión

        

          Según el mapeo configurado. Sin leer contenido ni consultar el sistema: misma
          entrada, misma salida, determinista.
        

        
Garantía: classify() pura, sin I/O.

      

      

        A2
        
Solo archivos regulares del nivel superior

        

          Nunca directorios, ocultos (salvo --include-hidden) ni symlinks. Ni siquiera se
          mueven los archivos de configuración cargados.
        

        
Garantía: filtros en planMoves().

      

      

        A3
        
Nunca sobrescribe ni pierde datos

        

          Ante colisión, sufijo name (1).ext. El dry-run no realiza ninguna
          escritura: plan y ejecución están separados.
        

        
Garantía: resolveUniquePath() + dry-run.

      

      

        A4
        
Idempotencia

        

          Ejecutar dos veces seguidas produce cero movimientos en la segunda: una corrida real
          deja la carpeta lista.
        

        
Garantía: verificado por tests.

      

      

        A5
        
Lo desconocido va a Others (o se omite), jamás se elimina

        

          Toda extensión desconocida o archivo sin extensión termina en la carpeta miscelánea o se
          reporta como omitido según configuración. Nada se borra.
        

        
Garantía: miscFolder / omitMisc.

09 Arquitectura: 4 módulos pequeños, cada uno con un trabajo

    

      Sin frameworks ni capas innecesarias: cuatro módulos TypeScript, cero dependencias en runtime y
      una frontera clara entre lo puro (clasificar, fusionar) y lo impuro (I/O).
    


    

      

        
config.tsconfig

        
Mapeo por defecto, validación JSON con type guards (nunca any), precedencia en capas y fusión por extensión.

        
DEFAULT_MAPPING · loadConfig() · mergeMapping() · parseFileConfig()

      

      

        
classify.tspuro

        
Clasificación pura por extensión: aislada para que un futuro clasificador MIME la reemplace sin tocar el resto.

        
extractExtension() · classify()

      

      

        
mover.tsI/O

        
Plan (scan + colisiones) separado de la ejecución (mkdir, rename con fallback EXDEV, dry-run). Errores por archivo sin detener el resto.

        
planMoves() · executeMoves() · resolveUniquePath() · moveFile()

      

      

        
cli.tsorquesta

        
Argumentos con util.parseArgs (estricto), orquestación config → plan → ejecución, reporte y códigos de salida.

        
runCli() · formatReport() · main()

      

    


    

      La frontera pureza/I-O. classify y mergeMapping son funciones
      puras (deterministas, sin efectos). Toda la I/O vive en config (lectura de JSON) y
      mover (disco). Esa separación hace que los tests de clasificación sean triviales y
      que el dry-run sea gratis: no hay que «simular» nada, simplemente no se ejecuta la etapa de
      escritura.
    

  







  

    
10 Aprendizajes del proyecto

    

      Qué se llevó el proyecto de cada tema — y una nota honesta sobre cuándo importan realmente los
      streams.
    


    

      

        FS
        
Filesystem

        

          readdir con withFileTypes distingue archivos, directorios y
          symlinks sin un stat extra por entrada. rename es una
          operación atómica; mkdir recursivo crea la carpeta completa.
        

        
Gotcha: ENOTDIR ≠ ENOENT cuando un componente de la ruta es un archivo.

      

      

        ST
        
Streams (cuándo importan, honestamente)

        

          En el mismo filesystem, rename es instantáneo y no copia nada. Los streams solo
          aparecen en el fallback cross-device (EXDEV): mover entre discos exige copiar, y
          stream/promises.pipeline copia sin cargar el archivo completo en memoria.
        

        
Veredicto: irrelevante para archivos chicos; decisivo para archivos de GB.

      

      

        CLI
        
CLI

        

          util.parseArgs en modo estricto con flags booleanos/string y posicionales;
          stdout = reporte, stderr = errores; código de salida 0/1 y la regla de
          oro: nunca llamar process.exit, solo fijar process.exitCode.
        

        
Lección: un CLI bien comportado es una API de terminal.

      

      

        CF
        
Configuración declarativa

        

          Precedencia en capas, merge por extensión (no reemplazo total) y validación con type
          guards sobre unknown. Un error de configuración es fatal y explícito,
          nunca un fallback silencioso.
        

        
Regla: fallar alto es más amable que adivinar.

      

      

        DS
        
Diseño: plan vs. ejecución

        

          Separar la lectura pura (plan) de la escritura (ejecución) habilita el dry-run
          sin efectos y reportes deterministas. El conjunto de reservas del plan evita
          sobrescribir entre movimientos del mismo plan.
        

        
Patrón: decidir todo primero, escribir después.

      

      

        TS
        
TypeScript nativo + TDD

        

          node --experimental-strip-types ejecuta TS sin paso de build; TS estricto con
          erasableSyntaxOnly y verbatimModuleSyntax. TDD estricto con
          node:test: RED → GREEN → triangulación, 50 tests en 3 suites.
        

        
Evidencia: 50/50 en verde + tsc --noEmit limpio.
