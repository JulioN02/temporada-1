1.El problema

Las operaciones diarias de una empresa —inventario, pedidos, notificaciones y control de cambios— suelen vivir dispersas en planillas, correos y herramientas inconexas. Esa fragmentación produce errores caros: vender stock que no existe, perder avisos críticos, pedidos sin estado claro y cero trazabilidad sobre quién hizo qué. Ningún proceso importante queda auditado, y el crecimiento convierte cada decisión operativa en un riesgo manual.

Por qué importa: el inventario debe reflejarse en tiempo real, la confirmación de un pedido no puede dejar estados parciales, las notificaciones tienen que llegar a la persona correcta en su idioma, y toda mutación debe quedar registrada de forma inmutable. Son requisitos de integridad de datos y de confianza, no solo de conveniencia.

Qué resuelve este capstone: construir una plataforma de operaciones donde los workflows automatizados orquestan inventario, pedidos y notificaciones. El núcleo técnico es la confirmación atómica de un pedido: en una sola transacción se valida el stock bajo bloqueos de base de datos, se descuentan los movimientos, se escribe la auditoría, se crean las notificaciones bilingües y se encolan los correos. Todo o nada, sin estados parciales observables. Además incluye RBAC de 5 roles y 19 permisos, un CRM, auditoría append-only, jobs durables y una SPA React completa con i18n español/inglés neutro.

2.El método aplicado

El objeto del problema cambia (una API y una base de datos, un servidor, una red); el método no. Este capstone se construyó con un núcleo transferible de resolución de problemas que se repite en cualquier proyecto, y cada etapa dejó evidencia concreta: 

PROBLEMA → ANALIZAR → DISEÑAR → DIAGNOSTICAR → IMPLEMENTAR → VERIFICAR → OPERAR → MEJORAR

3.Análisis y requisitos

Antes de escribir una línea de código, el problema se convirtió en un contrato verificable. El contrato v2 fusionado (spec.md, 1103 líneas) contiene 122 requisitos: 63 de la plataforma v1 más 59 añadidos por el cambio capstone-ui (SPA React + i18n). Cada requisito funcional tiene un escenario Given/When/Then que mapea 1:1 a un test nombrado con su ID (por ejemplo R-ORD-5). Esto demuestra capacidad analítica por tres vías: el requisito se define por su resultado medible (no por intuición), la cobertura es un gate automatizado (72/72 IDs del cambio capstone-ui en al menos un test, y 63/63 IDs de v1 en el backend), y cualquier desviación entre el contrato y la realidad se registra y se justifica en vez de ocultarse.

Cola de jobs durable sin añadir infraestructura operativa Redis + BullMQ, o pg-boss sobre el Postgres existente pg-boss v12 Usa el mismo Postgres: cero infra extra. Además permite el enqueue atómico en la misma transacción del negocio (same-tx), lo que da exactly-once sin outbox ni poller (R-NOT-6, R-JOB-4).

5.Diseño y arquitectura

El diseño responde directamente a los requisitos de integridad. Donde el contrato exige atomicidad, inmutabilidad, ausencia de polling y enqueued en la misma transacción, la arquitectura lo garantiza por construcción: una confirmación atómica que con locks de base de datos valida, descuenta, audita y notifica en un solo commit; un ledger de stock inmutable; una auditoría append-only; y un worker durable que solo consume lo ya commiteado.

Monorepo npm con dos workspaces: backend/ (API + worker en un solo paquete, Node ≥22 con TypeScript nativo, sin paso de build) y ui/ (SPA React 19 con Vite 6). API-first: todo flujo se expone como endpoints con DTOs zod, y el frontend consume exactamente el mismo contrato que genera la documentación OpenAPI.

Flujo de una request y de un evento

REQUEST:  HTTP → routes → controller (≤15 líneas) → service (framework-free)
                     → repository (SQL $1,$2 parametrizado) → PostgreSQL 16
                     └─ dto zod (fail-fast) → OpenAPI 3.1 → Swagger UI /api/docs

EVENTO (confirmación atómica de pedido, R-ORD-5 / §3.1):
  transacción única:
    order lock → advisory locks por producto (orden ascendente, sin deadlocks)
    → valida stock → inserta movimientos out (inmutables)
    → escribe auditoría → crea notificaciones in-app → encola emails
  commit-all o rollback-all. Sin estados parciales observables.

WORKER (worker.ts):
  pg-boss notification.send (retryLimit 5, backoff, DLQ=failed)
    → lee el snapshot almacenado de la notificación (nunca re-renderiza)
    → nodemailer → mailpit (dev) / SMTP real (prod)

  • api/ — cliente fetch con refresh single-flight acotado, módulos tipados por endpoint, tipos de contrato.

  • RBAC — roles, permissions, role_permissions, users (+locale).
  • CRM — customers (status active/inactive).
  • Catálogo — products, warehouses.
  • Órdenes — orders, order_items (snapshot de precio/nombre).

6.Implementación

La construcción siguió el método de forma disciplinada: cada slice vertical respeta la cadena routes → controller (≤15 líneas) → service (sin express/pg) → repository (SQL parametrizado) → dto, lo que mantiene la lógica de negocio independiente del framework y de la base de datos (R-NFR-4). Ambos workspaces comparten TypeScript estricto con los mismos flags (noUncheckedIndexedAccess, exactOptionalPropertyTypes, erasableSyntaxOnly) y el pattern const-types para derivar uniones sin literales sueltos.

Strict TDD con tests referenciados por requisito: cada requisito del contrato tiene un escenario y un test nombrado con su ID (RED → GREEN → TRIANGULATE → REFACTOR). El gate de cobertura de IDs impide que exista código sin contrato, y cada iteración dejó evidencia ejecutable.

8.Operación

El resultado no es un repositorio, es un sistema operado. El appliance Docker se construye con un gate de calidad interno (typecheck + tests + build de UI antes de empaquetar), corre como usuario no-root, expone HEALTHCHECK y se sirve completo —API + SPA— en un solo contenedor, verificable offline (R-PROD-1/2/7).

  • CI/CD → GHCR: push/PR corren typecheck + tests (backend y UI) + build antes del build de Docker; los tags v* publican la imagen en GitHub Container Registry (ghcr.io/<owner>/business-operations-platform) — .github/workflows/ci.yml y cd.yml.
  • Despliegue: runbook completo en docs/deploy-oracle.md — VM Ampere A1.Flex en Oracle Cloud Always Free ($0), Docker + compose, pull de GHCR y compose up; incluye backup con pg_dump y procedimiento de upgrade/rollback con migraciones aditivas e idempotentes.
  • Observabilidad: /api/health público (ping a la DB, usado por el HEALTHCHECK) y /api/status autenticado (versión, uptime, estado de la DB y colas).
  • Logs: pino JSON, una línea parseable por request (método, path, status, durationMs, requestId), con paths redactados para authorization, cookie, password y tokens (R-OBS-3).
  • Secretos: solo por env en runtime, validados al arrancar con fallo rápido y mensaje claro sin valores (R-PROD-5); jamás horneados en la imagen; .env.example documenta cada variable con valores en blanco.

9.Lecciones aprendidas

Aprendizajes reales del viaje de construcción, documentados en el verify-report y en los spikes (pg-boss tx y vitest+RTL).

  1. El enqueue atómico en la misma transacción existe y funciona. boss.send(queue, data, { db: { executeSql } }) con adapter de transacción inserta en pgboss.job dentro del withTransaction: rollback → el job desaparece. Esto eliminó la necesidad de outbox o poller (ADR-2 validado).
  2. El request path necesita un boss NUNCA iniciado sobre un pool compartido. Un boss iniciado corre timers de mantenimiento; stop() cierra su pool. La cola además debe existir antes del send, si no lanza "Queue does not exist".
  3. RTL no hace auto-cleanup con vitest globals:false. La primera corrida falló por DOM filtrado entre tests; la solución fue afterEach(() => cleanup()) en el setup. Detalle pequeño, efecto grande en suites de componentes.
  4. npm 11 gatea los postinstall. esbuild quedó sin binario al hacer npm install; hubo que aprobar scripts (npm install-scripts approve esbuild). Para CI/Docker se añadió --allow-scripts. Y @vitejs/plugin-react debe pinarse en 4.7.0: la línea 6.x exige Vite 8.
  5. La paridad RBAC se logra importando el registry real del backend. El test de la UI importa backend/src/permissions/registry.ts directamente (módulo const puro) y hace deep-equality con el mirror. Más fuerte que copiar la matriz a mano.
  6. El orden de los gates importa: dist-scan. El scan de secretos sobre ui/dist (R-UI-NFR-3) se vuelve vacuo si vitest corre antes de vite build en CI/Docker (early-return). Lección: build antes de test, o separar el scan a un paso post-build. El scan de fuente sí corre en todos lados.
  7. Los gates de paridad i18n son baratos y potentes. 236/236 claves por locale con fallo de compilación si falta una (keyof typeof), test de paridad bidireccional, scan de tokens prohibidos (vos/tenés/querés/sos/andá/che/dale) sobre UI y plantillas, y render al emitir con snapshot inmutable para que el worker nunca re-renderice.
  8. El regex de cobertura debe usar la misma convención que los IDs. El regex original de R-UI-NFR-6 no matcheaba IDs de dos segmentos como R-UI-CRM-1, así que el gate pasaba en silencio. Se endureció a multi-segmento y se añadió una lista estática para que el mismo gate corra dentro del contexto de build de Docker (donde openspec/ no existe).
  9. La spec se equivoca a veces; la verificación la corrige. "11 módulos" vs la matriz de 9 (bodegas plegadas en Stock); el transfer devuelve NEGATIVE_STOCK y no INSUFFICIENT_STOCK (el outcome UX es idéntico porque localizeError mapea ambos); y la lista de pedidos muestra #customerId porque el DTO no trae nombre de cliente.
  10. vitest serial para determinismo. fileParallelism:false + timeout 15s convirtieron una suite flaky en una gate determinista (217/217); los tests de concurrencia (R-ORD-5, R-STK-5) corren contra Postgres real, no contra mocks.
  11. Dinero float-free también en el front. Mostrar "12,50 €" / "$12.50" se hace formateando la parte entera del string D13 con Intl.NumberFormat (sin tocar floats) y el round-trip de entrada normaliza la escala a 2 decimales. Nunca Number() sobre dinero.

10.Posibles mejoras

El cierre del ciclo deja mejoras priorizadas a partir de la verificación y una lista de ideas post-v1. (Las opciones descartadas con su motivo ya están documentadas en la sección 4, Alternativas y decisiones; aquí solo quedan las mejoras futuras.)

  • S1 · Nombre del cliente en pedidos: añadir customerName aditivo a OrderListItemDto; hoy la columna muestra #customerId (el id es autoritativo, pero el nombre puliría la UX).
  • S2 · Nombres de rol localizados: claves i18n para los 5 roles en el chip de usuario (hoy muestra identificadores técnicos).
  • S3 · Toast para el fallo del toggle de idioma: el PATCH de locale falla en silencio (se autocura con backend-wins-on-boot), pero un toast lo haría más claro.
  • F1 · Orden del gate de dist: reordenar CI/Docker para build antes de vitest y que el scan de secretos de ui/dist no sea vacuo.
  • F3 · Comentario stale del Dockerfile: aclarar que openspec/ no está en el contexto de build.
  • E2E con Playwright: diferido de forma deliberada; complementaría vitest/RTL con flujos de navegador reales.
  • Websockets/SSE para notificaciones en vivo: hoy la SPA usa refresco on-demand y el badge se actualiza en navegación; un canal en vivo lo haría instantáneo (descartado en v1, locked).
  • Ventana de dedupe para low_stock: hoy cada cruce de umbral notifica; una ventana de tiempo evitaría ruido en operaciones muy activas.
  • Rate limiting y cache: out of scope en v1 (locked), pero natural como siguiente capa de hardening para producción compartida.

Modelo de seguridad

  • Auth: access token JWT 15 min (verify + typ + exp); refresh 7 días, SHA-256 en reposo, cookie httpOnly firmada (Secure en producción), rotación con detección de reuso (invalida la familia completa).
  • RBAC: 5 roles (admin, manager, operator, viewer, auditor) × 19 permisos; chequeo por request contra la BD; registro TS con paridad SQL testeada.
  • Contraseñas: política 12–128 con ≥1 letra y ≥1 dígito; bcrypt cost 10.
  • Frontend: token solo en memoria; 401 → refresh single-flight → 1 reintento → logout acotado; guards de ruta y acción.
  • Secrets: env-only validado al arrancar; pino redact (authorization, cookie, password, *.token, SMTP); sin secretos en el bundle.

Observabilidad y jobs

  • /api/health público (ping DB) usado por el HEALTHCHECK de Docker; /api/status autenticado con colas.
  • pino: una línea JSON por request (método, path, status, durationMs, requestId), redactada.
  • Jobs: cola notification.send, retryLimit 5 con backoff, dead-letter a failed, reintento manual por API/UI, auditoría del ciclo de vida.
  • Notificaciones: 7 tipos con matriz canal-por-tipo (in-app/email); plantillas bilingües; snapshot inmutable renderizado al emitir; SMTP solo en worker.

Usar la SPA

Login con usuario/contraseña. El sistema tiene 5 roles: admin (todo: usuarios, auditoría, jobs, productos/bodegas), manager (operaciones + productos/bodegas + jobs), operator (clientes, pedidos, ajuste de stock; sin transferencias), viewer (solo lectura) y auditor (lectura + auditoría). El sidebar y los botones reflejan el rol en cada sesión; el idioma se alterna con el toggle ES/EN (persistente).

  • Dashboard: estado del sistema, KPIs, alertas de bajo stock, notificaciones recientes y refresco on-demand.
  • Clientes / Productos / Bodegas (CRM): CRUD con búsqueda, paginación y estados; los inactivos nunca se borran.
  • Stock: niveles con insignia de stock bajo, historial de movimientos, ajustar (qty firmada + motivo) y transferir (from ≠ to).
  • Pedidos: crear con editor de líneas, confirmar (confirmación atómica, UI optimista con rollback limpio ante 409) y cancelar con motivo.
  • Notificaciones: listar las propias, filtrar no leídas, marcar leídas; badge en el sidebar.
  • Gobernanza: auditoría (admin/auditor), usuarios (admin), jobs con reintento (manager+).
